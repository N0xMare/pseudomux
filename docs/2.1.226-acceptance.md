## 1. What "verified" means here

`docs/path-b.md` §0.3 rule 5: *an absence is only evidence if something would have shown a
presence.* Applied to a turn, "it returned something" is not success. Every paid turn below carries
a **nonce plus an arithmetic result**, so the answer cannot come from a cache, a template, a
truncated read of a neighbouring transcript, or a fixture:

    Nonce: KX41. Add 17 and 25. Reply with exactly the nonce, a hyphen, and the sum, and nothing else.

The nonce proves the bytes came from *this* turn; the sum proves a model produced them. Both were
checked mechanically for all nine arithmetic turns. Instance reuse is proven by **pid identity**,
not by latency alone — a reused instance is the same operating-system process, and `ps` says so.

Rule 4 of the same section applies to tokens: `input_tokens` alone is not a turn's input. Every
usage figure below is quoted as the full `UsageBreakdown`.

## 5. Pool mechanics under real load

### 5.1 Reuse, and the relaunch it avoids

A2 was served by **pid 56424, the same process that served A1** — `ps` before and after. Cold 4334 ms
against warm 2714 ms is a **1620 ms** saving on this host. `docs/path-b.md` §6 quotes the relaunch
it avoids as ~4.4 s (a TUI launch); a cold pool ask here cost 4334 ms end to end including the turn,
and a warm-class mint alone completed **within 1265 ms of daemon boot start** (declared warm floor,
boot to `idle`). So the relaunch pmux avoids is real but cheaper on this host than the recorded
figure; the saving is what matters and it is 1.6 s per turn.

A2 also caught the **rewarm** (`should_rewarm`, `crates/service/src/pool/mod.rs:1096-1100`): checking out the last idle
instance of a class while capacity is free mints a spare, so `live` went 1 → 2 and a second pid
appeared — behind the caller, who waited for neither. A4 caught the **cold swap**: the sonnet/low
spare (pid 57048) was destroyed and a sonnet/high instance minted into slot 1 **epoch 1**, with
`live` steady at 3 and `leaked: 0`. Rules 1 and 3 of `admit_once`, observed live.

## 6. The defect: `pmuxd` does not handle `SIGTERM` during Path B startup

**This is not about Claude 2.1.226. It is the one reliability finding of this session.**

`shutdown_signal()` was an `async fn`, and it is where `signal(SignalKind::terminate())` was
called — that future is only polled once `serve_until` is entered. The shape is no longer in the
tree, so the citation is to the doc comment that now records it: `bin/pmuxd/src/main.rs:762`, on the
`ShutdownSignals` value that replaced it, quotes the old `async fn shutdown_signal()` and says why
an `async fn` in argument position installed nothing until `NativeService::start` had returned. The
call it was passed to is `serve_until` (`bin/pmuxd/src/main.rs:763`).

Everything before it runs with `SIGTERM` at its **default disposition** — including `NativeService::start`,
which is where `Pool::start` mints the entire declared warm set. The window is therefore exactly as
long as the warm mint, and scales with `--path-b-warm` up to the cap of 15.

Measured, with a positive control, counting processes by absolute executable path:

| `SIGTERM` at | exit | slot trees left | socket | log lines |
| --- | --- | ---: | --- | ---: |
| 0.5 s, warm=2 | **143** | 1 | **stale, left behind** | 1 |
| 1.5 s, warm=2 | **143** | 2 | **stale, left behind** | 1 |
| 0.2 – 3.0 s, warm=3 | **143** | 1–3 | stale | 1 |
| **8 s, warm=2 (control)** | **0** | **0** | removed | 3 |

Exit 143 is the kernel, not pmux. Three consequences, all reproduced:

1. **Residue.** One slot epoch tree per instance the mint had reached, plus a stale socket file,
   because `socket_guard.cleanup()` never runs.
2. **Silence.** The log holds only the one raw `writeln!` startup record. The `tracing` layer is a
   `tracing_appender::non_blocking` writer whose `WorkerGuard` is never dropped, so every buffered
   record is lost — including the `pmuxd protocol v1 listening` record that had already been emitted, which `info!` writes with
   `socket_path` at `bin/pmuxd/src/main.rs:648`.

   The `EnvFilter` at `bin/pmuxd/src/main.rs:1153` sets `pseudomux_service=warn`.

   That filter admits `ERROR`, so a `path_b_leak` record would pass the
   filter; it just never reaches the file.
3. **The next start refuses.** `mint_roots` (`crates/service/src/pool/mod.rs:2095`):
   `epoch directory /…/poolparent/0/0 already exists; the pool never adopts a tree it did not
   create`. Refusing is correct — the pool must not adopt a tree it did not create — but the
   operator gets it with nothing in the log explaining where the tree came from.

**Severity, honestly bounded.** No process is leaked: the `--owner-stdin` rmux sidecar reaps itself
and its Claude children within 1 s in every case, verified with a corrected counter (§9 records that
my first counter was wrong). And recovery is not permanent: a refusing start consumes trees as it
goes, so restarting clears it. **One restart sufficed in both bounded trials**; in an earlier
unbounded chain two consecutive restarts refused before one succeeded. I did not characterise that
distribution. So this is a startup wart with a confusing failure message — not a brick, and not a
process leak. It is reachable by
anything that stops a service during startup — a supervisor with a short start timeout, a rollout, a
`systemctl restart` that races itself, or a test harness.

**A Path A-only daemon shows no window** (exit 0 at every offset from 50 ms), because there is no
warm set to mint. The window is a Path B property.

### 6.1 CLOSED 2026-08-09 — and the distribution this section did not characterise is exponential

The paragraph above is the one that needed the follow-up, and its verdict — *"a startup wart with a
confusing failure message"* — is the part that did not survive being measured. **The chain is
`2^w − 1` refusing restarts for a warm set of `w`**, which is 32,767 at the owner's 15-instance cap.
The mechanism is that a refusing start erases the ONE tree it collides with and **abandons every
tree it had already minted before reaching it**, because `bin/pmuxd` drops the `NativeService` a
failed `NativeService::start` never handed it. So the leftover set moves

    L  ->  (L \ {min L})  union  {0 .. min L - 1}

and every one of those transitions was observed, not assumed. Re-run at this HEAD's parent with
`--path-b-warm claude-sonnet-5/low=3` against real Claude 2.1.226, SIGTERM 2.6 s in:

| restart | leftover before | leftover after |
| ---: | --- | --- |
| 1 | `0/0 1/0 2/0` | `1/0 2/0` |
| 2 | `1/0 2/0` | `0/0 2/0` |
| 3 | `0/0 2/0` | `2/0` |
| 4 | `2/0` | `0/0 1/0` |
| 5 | `0/0 1/0` | `1/0` |
| 6 | `1/0` | `0/0` |
| 7 | `0/0` | — |
| 8 | — | **served** |

Seven refusals, `2^3 − 1`, from the same three trees this section's own table records as the residue.

**Fixed, and measured on the same harness.** The handlers are installed before anything is minted;
a failed start drains what it minted before returning; and the refusal names the situation rather
than only the rule.

| | this section | at the fix |
| --- | --- | --- |
| exit | **143** | **0** |
| trees left | `0/0 1/0 2/0` | **none** |
| socket | stale, left behind | **removed** |
| daemon log | 1 line, the raw `writeln!` | **3**, incl. `pmuxd protocol v1 listening` and `pmuxd stopped` |
| refusing restarts to recover | **7** | **0** |
| refusing restarts from 3 *planted* trees | 7 | **3** — one per tree, strictly shrinking |
| signal → exit | 18 ms (a kernel kill) | **4,560 ms** |

That last row is the disclosed cost and the one thing the fix deliberately does **not** buy: the
signal is now observed rather than fatal, but it does not cancel the mint. A daemon signalled 2.6 s
into a three-instance warm set finishes minting all three and then tears them all down. Racing
`NativeService::start` against the signal is the one repair that is unavailable — main holds no
service handle until it returns, so dropping that future orphans exactly what `start_pool`'s own
comment says must stay accountable.
